# Contributing to Zirv Flow

Follow the [Code of Conduct](CODE_OF_CONDUCT.md). Report vulnerabilities through
our [security policy](SECURITY.md).

## Reporting bugs and requesting features

Use the [GitHub issue forms](https://github.com/Glubiz/zirv-flow/issues/new/choose).
Include enough detail to reproduce a bug or explain the problem a feature solves.
Never include secrets, tokens, or personal data of your contacts in reports.

## Development setup

Install the stable Rust toolchain, then run from your checkout:

```sh
cargo install cargo-nextest
cargo build
```

For what the project is and where it is going, see the [README](README.md).

## Making changes

Branch from `main`; never commit directly to `main`. Keep diffs focused and mirror
existing naming, structure, and style. Tests stay inline in `#[cfg(test)] mod tests`;
`tests/fixtures/` is data only.

Follow the enforced crate, feature-module, registry and frontend boundaries in
[architecture section 5](docs/architecture.md#5-module-and-crate-layout). Put new
code behind the owning module's public surface; never loosen a boundary check to
make a change pass.

Size verification to the change using [CLAUDE.md](CLAUDE.md#build-and-verify-by-tier):

- Docs or comments: run `cargo fmt -- --check` if Rust was touched; otherwise no checks.
- Code: run `cargo build`, `cargo nextest run <filter>` for touched modules, and
  `cargo clippy --all-targets -- -D warnings`.
- Before opening or updating a PR: run all four gates below once.

## Before opening a PR

### Parser properties and fuzzing

The normal suite includes bounded JSON and fixture-mutation properties for segment ASTs,
manifests, template documents, sanitizers and flow graphs. They use 64 cases and seed 387;
`ZIRV_FLOW_FUZZ_CASES=2000` raises the count. Each checked sample has a five-second budget.
Run just this floor and the fuzz-target drift guard with:

```sh
cargo nextest run --no-fail-fast -p zirv-flow-core -p zirv-flow-segments -p zirv-flow-connectors -p zirv-flow-templates fuzz_
```

The standalone `fuzz/` workspace runs the same `check_*` functions under libFuzzer on Linux.
From the repository root:

```sh
rustup toolchain install nightly-2026-10-26 --profile minimal
cargo +stable install cargo-fuzz --version 0.13.1 --locked
bash fuzz/seed-corpus.sh
for target in segment_ast manifest template_document sanitize_source; do
  cargo +nightly-2026-10-26 fuzz run "$target" -- -max_total_time=600 -max_len=800000 -timeout=10 -rss_limit_mb=2048
done
```

Seeding copies existing fixtures and goldens; it preserves discoveries already in `fuzz/corpus/`.
`fuzz/Cargo.lock` is generated by the first build and uploaded with CI artifacts, not committed.
The [fuzz workflow](.github/workflows/fuzz-nightly.yml) runs nightly (600 seconds per target),
accepts a manual budget of 1–1200 seconds, and runs 60 seconds per target on PRs touching `fuzz/`.
It caches each corpus and uploads crash artifacts, including on failure. The existing
`SECURITY.md` critical-files rule for `.github/workflows/*` covers this workflow.

Reproduce a downloaded crasher with
`cargo +nightly-2026-10-26 fuzz run TARGET PATH_TO_CRASHER`.
Before fixing it, add the reproducer to the owning crate's inline `#[cfg(test)] mod tests`,
as literal bytes or a `tests/fixtures/` file. Fix the bug in the same change and keep that
regression test. Fuel and output limits do not bound intermediate template allocations;
libFuzzer also enforces a ten-second timeout and a 2 GiB RSS limit.

### Full verification

```sh
cargo build
cargo nextest run --no-fail-fast
cargo fmt -- --check
cargo clippy --all-targets -- -D warnings
```

Bump the version in `Cargo.toml` above its base version on `main` whenever the
diff touches `src/`, `crates/`, `Cargo.toml`, `Cargo.lock`, or `build.rs` -- CD's release
step is idempotent on an already-published version, so a docs/CI-only PR needs
no bump. Run `cargo build` to update `Cargo.lock` and include it.

Commit subjects use `type(scope): summary`, with types such as `feat`, `fix`,
`docs`, and `chore`; for example, `fix(segments): handle empty audiences`.
Do not include `Co-Authored-By` or `Generated with Claude Code` lines in commits.

## Pull requests

Open a PR targeting `main` with one logical change and explain what changed and
why. CI runs on pull requests to `main` and is the merge gate.
